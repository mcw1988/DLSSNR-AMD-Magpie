# `tools/` — 纸面模型与回归

四个工具分工不同，**别拿错**（拿错会得出完全不同的结论）：

| 工具 | 干什么 | 输出 | 什么时候用 |
|---|---|---|---|
| `slot_model.py` | **纸面预测**：三种调度（上游单槽 / 阶段 1 多槽 lag0 / 阶段 2 lag1）的帧时间 | 控制台对照表 + 五点实测校准 | 改设计、改判据、怀疑"求和 vs 取大"时；**不需要 GPU** |
| `test_slot_model.py` | **回归**：钉住 `slot_model.py` 的结论不被悄悄改坏（QA 维护） | pytest / 断言 | 改了常数或调度结构之后 |
| `../scripts/measure-gpu-busy.ps1` | **G0 判别**：`\GPU Engine(*)\Utilization Percentage` 按 PID 累加，算 `ratio = 每帧引擎忙秒 ÷ frame_time` | 三档判据 + CSV | **动手做阶段 2 之前必须先跑**；它决定台阶存不存在 |
| `../scripts/measure-fsr-ring.ps1` | **现场采集汇总**：从 `magpie.log` 里抠帧时间与 `fsr3-slot:` 读数，按配置汇总并按 §6 判通过/失败 | 一行 CSV + `-Summary` 对照表 | 真机跑完之后，把数字变成"通过/失败" |

一句话顺序：**`measure-gpu-busy.ps1`（能不能做）→ 打补丁 → `measure-fsr-ring.ps1`（做到没有）**。
`slot_model.py` 从头到尾只提供"应该发生什么"，不提供"实际发生了什么"。

### 输入口径：三个常数各自来自哪个实测点

全部来自 `docs/findings.md` 的「2026-11-02 补2：A/B 天花板实测闭环」（9070 XT，4K 窗口，无 FG）：

| 常数 | 值 | 来源 | 含义 |
|---|---|---|---|
| `CAPTURE_PRESENT` | 6.7 ms | **B1**（150 fps / 6.67 ms，仅 `FrameRate_Filter`） | 捕获/呈现的固定底，占帧时间 83% |
| `SLOT` | 1.4 ms | **B1 − B2**（150 → 123–125 fps，只留 `FSR4_SR`） | 整套 FSR4 槽位：两次 4K 拷贝 + `Flush` + 双向围栏 + 放大 |
| `NET_1X` | 13.7 ms | **A 组 s=1.0**（47 fps / 21.5 ms）反推 | scale 1.0 档的网络耗时；其它档按 `scale²` 缩放 |

四点 A 组（1.0 / 0.5 / 0.35）加两个天花板共**五点**，模型残差 ≤ 0.3 ms（脚本每次都会重算并打印）。

> 常数是**从这五点反推**的，所以那张校准表是**自洽性检查**，不是独立验证。它的用处是：
> 改动模型结构（比如把 `slack` 从 2 改成 1、把某个 `max` 改成相加）时，能立刻看出五点会不会崩。

### 怎么用实测反推参数

- **先看残差**：`single` 一列与五点实测的 `Δms` 必须 ≤ 0.4（或 `Δfps` ≤ 0.5），否则先怀疑常数被重测过，
  改 `CAPTURE_PRESENT / SLOT / NET_1X`，再回头看结论。
- **再看 δ 敏感性表**（脚本第四节）：`1.4 ms` 里有多少落在**岛内**决定了 1.0 档的预测值——
  δ=1.4（全算进岛，最保守）→ 66.2 fps；δ=0.6 → 69.9 fps（roadmap 的"约 70"）。
  两者差 0.80 ms，就是这笔不确定量。验收取 **66 为通过线**，>70 记超预期。
- **0.5 / 0.35 档不受 δ 影响**（`max` 由 D3D11 侧的 8.1 ms 决定），所以**主验证点放在 0.5 档**：
  它既是"取大"最干净的证据，又不吃 δ 的不确定性。

### 适用边界（重要）

1. **这是纸面模型，不是实测。** 它不访问 GPU、不读日志、不测任何东西。
2. **`ring_lag1` 的预测只在 G0 通过时成立。** GPU 忙时间已被占满时 `max` 拿不到东西，
   整列作废——判定权在 `scripts/measure-gpu-busy.ps1`，不在这里。
3. **模型被证伪时改模型，不要改文档结论。** 顺序是：实测对不上 → 先查常数的口径（B1−B2 是
   同一台机器同一次运行吗？）→ 再查调度结构（依赖关系写错了吗？）→ 最后才怀疑设计假设本身。
   反过来把模型调成"能对上实测"，这个文件就再也不能证伪任何东西了。
4. `ring_lag0 == single` 是**可证伪的设计断言**（阶段 1 收益为 0，`docs/multislot.md` §6.1 A2：
   掉 ≥3 fps 才算失败）。谁把阶段 1 当收益项，先看这张表。
5. `harvestMiss` 只按"岛是否比帧间隔长"给上限估计（s=1.0 时岛 ≈ 帧间隔 → ≈100%），
   **不预测抖动**。真实比例看 `magpie.log` 的 `fsr3-slot: … harvestMiss=k/120`。
