# mochinr：把 mochizuki 运行时接进 FSR 槽位（v0.4）

**一句话**：从 v0.3 的「present 层降噪」改为「**FFX 放大调用内部、放大之前**降噪」——
mochizuki 权重现在和 lmxxf 站在同一条挂载点上，喂给放大器的已经是降噪后的帧。

---

## 1. 为什么换位置

v0.3 的 mochizuki 跑在 present 层（ReShade 的 add-on 在呈现时处理），这带来两个结构性代价：

| 现象 | 根因 |
|---|---|
| 开补帧（FG）后 NR 每帧被跑 N 次 | present 层看到的已经是补帧后的呈现帧 |
| NR 只能作用在最终画面 | 放大器（FSR）在它之前就已经跑完了 |
| 帧率越高越容易掉帧、闪烁 | 网络来不及跑完整帧率，跳帧就原样输出 |

上游 lmxxf 的 add-on 不是这么做的：它拦截 `ffxDispatch`，在**效果链内部**处理。
v0.4 把 mochizuki 搬到同一个位置。

```
v0.3:  捕获 → 拉伸/放大(FSR) → 帧率过滤 → 补帧 → present ← (NR 在这里，每帧 N 次)
v0.4:  捕获 → [NR] → 放大(FSR) → 帧率过滤 → 补帧                    ← (NR 在放大之前)
```

## 2. 实现契约（照上游源码，MIT）

关键在**时序**：`ffxDispatch` 是「录制期」调用，此刻颜色纹理里还是上一帧内容，
不能就地跑网络。上游的解法不是绕开，而是把工作挪到提交期：

1. **捕获并吞掉**：`ffxDispatch` 里只读描述符、记录资源，然后 `return 0`，一步 GPU 工作都不做。
2. **钩提交**：`ID3D12CommandQueue::ExecuteCommandLists`（虚表 slot 10）里，在宿主真正提交的那一批
   列表中按指针身份找到被武装的 list，把批次**劈成两段**：`[0..at]` 先提交，网络跑完，再提交 `[at+1..]`。
3. **用宿主的队列**：自己的 allocator/list 环跑在**宿主队列**上，队列顺序本身就是同步，
   不需要任何围栏等待。
4. **重放**：把原 `ffxDispatch` 写进我们自己的 list 重放，游戏自己的 list 一个字节都不动。

### 踩过的坑（全部有日志/崩溃记录支撑）

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | 崩溃，AV 落在 upscaler 内部 | 两个导出（upscaler / loader）共用一个 original，互相递归 | 一个 hook 一个 original |
| 2 | 崩溃，`ucrtbase` `0xc0000409` | 内层调用被重复捕获，外层拿到 0，SDK 状态崩坏 | 嵌套深度闸门（上游 `shim_depth` 同款）+ 未认领捕获立即重放 |
| 3 | 黑屏，`replay fault 0xc0000005` | 重放时传了**调用者**的 `void**`，栈帧已失效 | 捕获时解引用，重放传自己那份的地址 |
| 4 | 重放崩在 `D3D12Core`，读 `+0xc` | 命令列表建在队列设备上，而 FFX 上下文在另一个设备 | 用 `desc->commandList->GetDevice()`（虚函数，能穿透 ReShade 包装；`QueryInterface` 拿不到） |
| 5 | 设备被锁死 `0x887A0001` | 记录了 `StateBefore == StateAfter` 的冗余状态转换（非法调用） | 相同状态不记屏障 |
| 6 | 驱动 TDR | 把网络输出**拷贝**回颜色纹理，对他人纹理做了状态假设 | 不拷贝：直接把放大器的颜色输入指针指向网络输出（上游 `fed = Delivered()` 同款） |
| 7 | 高帧率下约 25 秒必崩 | `Retire` 早于 GPU 读完，私有缓冲被下一帧复用 | `Retire` 延迟到自己的围栏越过该帧 + 在飞上限 |
| 8 | `ntdll` 堆损坏 `0xc0000374` | 延迟释放表被两个线程同时改（渲染线程 push / ReShade 事件线程 erase） | 加锁；另修每帧一个 COM 引用泄漏 |

## 3. 参数面板

ReShade Home 页签下的 **mochinr 降噪** 面板（中文，四页签）：

- **网络**：启用、层数、渲染率、细节/色彩强度、历史重置；顶部显示**实际渲染分辨率**与网络 GPU 耗时
- **风味**：风格、强度、局部色调/结构、皮肤结构、自动遮罩、高光保护、色度钳制、细节稳定、
  链式历史、跟随输入分辨率、多层后续参数
- **计时**：会话状态、分辨率、已合成/跳过帧、CPU 每帧四项分解、在飞帧数、队列深度
- **调试**：显示视图（正常/代理/纯网络/差分/着色）、保存

> 参数不走 `LmxxfNrFrameInfo`：`MochizukiNrControls.renodx` 默认为 1（RenoDX 阶段），
> 该阶段**不使用** frame info 里的层数/渲染率/强度，改由 `reno_*` 字段接管，
> 必须经 `MochizukiNrSetControls` 下发。这是「面板除了开关全都无效」的真正原因。

## 4. 实机结果

效果组 **NR-preupscale**（`FSR4\FSR4_SR` 单效果器 + mochinr），WoW 正式服，9070 XT：

| 项 | 数值 |
|---|---|
| 输入 | 1920×1080（网络同尺寸） |
| 输出帧率 | **110–130 fps** |
| 每帧 CPU | 0.17 ms（Vulkan 围栏 0.09 + 提交 0.05 + 录制 0.02） |
| 稳定性 | **已承认：帧率尚不稳定**，高负载 / 分辨率变化时仍有起伏 |

对比 v0.3：同组 lmxxf 78–80 fps、ACO 纯 HLSL 桩 107–108 fps（两者 NR 位置不同，不可直接比较）。

## 5. 推论（未实测，需标注）

- **补帧**：NR 现在位于放大之前，补帧只看到降噪后的帧，**理论上已解决「mochi 运行时移植后无法开 FG」**
  的问题。**尚未实测。**
- **AMOF 光流**：补帧若需要光流，光流应当配置在补帧效果上而非 NR 上；该链路**未验证**，
  闪烁是否会随位置改变而消失也**不确定**。

## 6. 已知问题

1. **性能**：降低网络渲染率会降低 GPU 负载与功率，但**帧数不升**；游戏内限帧始终高于
   捕获/输出约 15–20 帧（已排除游戏限帧干扰）。嫌疑：D3D12 ↔ Vulkan 围栏造成的帧内串行。
2. **输入分辨率**：仅 1080p 实测；更高输入未验证。
3. **UI**：面板可用，但版式与术语仍待打磨。

## 7. 后续方向

- 优化 UI 界面（版式、分组、术语）
- 修正性能表现（消除帧内串行，而非降低质量）
- 适配 1080p 以上实机输入
- 调优 NR 效果风味
- 适配 MFG（多帧生成）
