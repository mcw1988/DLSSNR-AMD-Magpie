# 2026-10-31 调优日志：mochizuki 从 ~60 帧到 84 帧

本日目标：在不降低渲染分辨率、不换权重、不换运行时版本的前提下，把
`Magpie 0.6.11 + ReShade 6.8 + OpenNR 0.7.15 + mochizuki 0.5.8` 的实机平衡点抬上去，
并把“为什么这些改动不影响画面”逐条说清楚。

最终结果：**平衡点 64 → 84 fps（+31%）**，其中最大的一笔（+9 fps）来自关闭
`XeSS_SR` 上那个没有消费者的 AMDOF 光流。

---

## 1. 结果一览

| 阶段 | 平衡点 | 每帧预算 | 关键改动 |
|---|---|---|---|
| 起点 | ~64 fps | 15.6 ms | Motion=1、History=1、SR 上挂 AMDOF |
| 关 Motion | 68–75 fps | 13.3–14.7 ms | `Motion=0`，不再算 4K FFX 光流 |
| 关 History | 71–75 fps | 13.3 ms | `History=0`，断开时域历史 |
| **关 SR 上的 AMDOF** | **84 fps** | **11.9 ms** | `opticalFlowMethod=0`（无） |

> 起点的 64 与后来的 75 之间还夹着一批“抬游戏限帧反而掉帧”的观测，见第 4 节。

---

## 2. 预算模型：三个观测互相验证

同一天、同一场景、同一分辨率（4K 输出，NR 网络 1920×1080）下的三组观测：

| 状态 | 平衡点 | 每帧 |
|---|---|---|
| NR 开 + AMDOF 开 | 75 fps | 13.33 ms |
| NR 开 + **AMDOF 关** | **84 fps** | 11.90 ms |
| NR 关 + AMDOF 开（游戏限 125） | 125 fps | 8.00 ms |

三式联立，解出三个分量：

```
游戏自身渲染      ≈ 6.6 ms
NR 总计           ≈ 5.3 ms   （网络 3.3 + 桥接/双向拷贝 2.0）
AMDOF             ≈ 1.4 ms
```

校验：

```
6.6 + 5.3 + 1.4 = 13.3 ms -> 75 fps    ✅
6.6 + 5.3       = 11.9 ms -> 84 fps    ✅
6.6 + 1.4       =  8.0 ms -> 125 fps   ✅
```

三组观测误差都在 1 帧内，模型闭合。这是今天最有价值的产出：之后所有讨论都可以
用这张账来算，不再靠猜。

其中 NR 的 5.3 ms 与独立基准（`nrbench.exe`，1920×1080、ACO、CC_SMALL_FP8）测到的
网络 3.40 ms 互相印证，差额约 2.0 ms 是 4K 入/出拷贝与 D3D12↔Vulkan 桥接。

## 3. 逐项改动，以及为什么对画面几乎没有影响

### 3.1 `Motion=0`（NR 不再计算运动矢量）

- 改动：`amd-nr.ini` 的 `Motion` 由 1 改 0；面板里对应 “Motion” 勾选框。
- 收益：约 2.3 ms（64 → 68–75，多次顶到当时的游戏限帧 75）。
- 为什么影响小：NR 的时域重建失去运动矢量对齐，但**静态区域与缓动镜头不受影响**；
  影响只出现在快速平移/转身时的边缘，表现为轻微拖影。
- 代价：已在实机确认“拖影不明显”。若不能接受，打开 Motion 即回到 64 帧档。

### 3.2 `History=0`（断开时域历史）

- 改动：`History` 由 1 改 0。
- 收益：约 3–4 fps（71–72 → 75）。
- **这一项有可见代价**：时域历史关闭后，逐帧修正不再累积，实测出现**一定程度的闪烁**。
  这是性能与画质的真实权衡，不是“无影响”。
- 后续方向：优先用别处省下的时间把 History 开回来；若要留在关闭状态，可试
  `OutputSmooth` / `OutputSmoothLimit`（ini-only，面板无控件）压制逐帧跳变。

### 3.3 `opticalFlowMethod=0`（本日最大单笔收益）

- 改动：效果组里 `XeSS\XeSS_SR` 的 `Optical Flow Method` 由 1（AMDOF）改为 0（无）。
- 收益：**75 → 84 fps（+9 帧，约 1.4 ms）**。
- 为什么完全不影响画面：`effects\XeSS\XeSS_SR.hlsl` 的全部着色器代码只有一行

  ```hlsl
  MF4 Pass1(float2 pos) { return INPUT.SampleLevel(sam, pos, 0); }
  ```

  它是个直通采样桩，**不消费光流贴图**。该参数只决定 Magpie 是否为这个效果每帧
  额外产出一张 4K 光流贴图；在补帧被移除后，这张贴图没有任何消费者。
  关掉它，输出的像素一个都不变。
- 佐证：Magpie 日志里每帧一条

  ```
  Frame Guidance AMD OF timing frameId=... opticalFlowSubmit=0.050 ms totalSubmit=0.052 ms
  ```

  该行只记录 CPU 提交耗时（0.05 ms），GPU 侧的开销体现在平衡点上（1.4 ms）。

### 3.4 `Scale=0.5` 与 `CC_SMALL_FP8`（确认项，未改动）

```
the FP8 network (VK_EXT_shader_float8)
building CC_SMALL_FP8 at 1920x1080, VkFormat 37, ... 1 pass
```

网络本来就是 1080 档的轻量 FP8 权重（`MochizukiOriginalModel=0`），与对照运行时
（lmxxf 的 `DLSS5_NETWORK_HEIGHT=1080`）同尺寸，可直接对比。本日未改动。

### 3.5 与画面无关、但被验证过是“零收益”的两项

```
Inline=0        # engine runs async, so the game's queue does not wait for the network
D3D12Wait=0     # no present waits for the last evaluation
```

预期是解除串行等待，实测：`frame 37080 processed (0 skipped)`，fence 全程 5.12–5.52，
与改动前一致。说明 present 本来就没被 NR 挡住，这段等待不在我以为的位置。
两项保留（无害），但**不要再把它们算作优化项**。

## 4. 负结果：抬游戏限帧为什么会让帧数变低

现象：把游戏内限帧从 75 抬到 80+，Magpie 输出先冲到 80.6，随后回落到 74–75。

```
14:21:25-14:21:46   80.6 fps   fence 5.52
14:21:47-14:22:10   74.6 fps   fence 5.52
14:22:36-14:22:58   74.0 fps   fence 5.41
```

fence 只涨了 0.2 ms，帧时间却掉了 1.1 ms —— 差额在游戏侧。机制是：抬上限 → 游戏提交
更多帧 → GPU 功耗顶到上限 → 频率回落 → 单帧时间变长。80.6 是吃掉 boost 余量的瞬时值。

再进一步：**完全不限帧时，游戏跑到 150+，Magpie 掉到 60 多，fence 冲到 14.65 ms**。
两个进程抢同一块 GPU 时游戏占优，Magpie 每帧要多等 7 ms。

结论：

- 抬限帧不是提速手段，**游戏限帧应当设在“刚好等于产能”的位置**；
- 判断产能要用“平衡点扫描”（同一配置下试两个上限，取对齐点），不要看 fence：
  **fence 会随预算水位漂移**（NR 关掉后反而从 5.3 涨到 7.0），只能同状态前后比。

## 6. 下一步：加入 FG 之后会遇到什么

### 6.1 第一个要测的量：NR 是否按“呈现帧”评估

历史数据（2x 补帧、NR 挂 present 时）：会话 3311 帧 / 49.1 s，同期内容帧 33.6 fps，
比值 **2.00** —— NR 对每个被呈现的帧都跑一次。

判定方法（无需改配置）：跑 30 秒，取 `amd-nr.log` 里

```
swapchain going away (resize 0) after N frames
```

的 N，除以同期内容帧数。

| 比值 | 含义 | 处理 |
|---|---|---|
| ≈2 | NR 仍在 present 层、成本随倍率翻倍 | 需把 NR 挪到 FG 之前（见 6.3） |
| ≈1 | NR 只跑内容帧 | 直接按 6.2 的预算选倍率即可 |

### 6.2 预算表（按本日实测分量推算）

```
游戏 6.6 + NR 5.3×N + AMDOF 1.4 + FG 自身
```

| 配置 | 每帧 | 原生 | 输出 |
|---|---|---|---|
| 仅 NR（无 FG） | 11.9 ms | 84 | 84 |
| NR ×2 + FG 2x | ≈ 20.9 ms + FG | ≈ 45 | ≈ 90 |
| NR ×1 + FG 2x（需 6.3 成立） | ≈ 15.6 ms + FG | ≈ 60 | ≈ 120 |

`FG 自身` 未单独测出，需要用 `仅补帧` 组与 `NR-mochizuki` 组对比后补上。

### 6.3 若比值为 2：把 NR 挪到链内（唯一不牺牲安全的解法）

Magpie 本体自带一个**链内同分辨率降噪槽位**：

```
effects\DLSSNR\DLSSNR_AI_Filter.hlsl
// Experimental NVIDIA DLSS neural same-resolution filter.
// The native D3D12 backend replaces this pass...
```

它跑在 FG 之前，正是需要的位置；但后端是 NVIDIA NGX（`nvngx_dlssnr.dll`），
在 RDNA4 上不可用。Magpie 自身源码不在发行包内（`sources\` 只有 OptiScaler 分支与
lmxxf 的构建脚本），无法直接改。

可行路径：写一个**替身 `nvngx_dlssnr.dll`**，实现 Magpie 导入的那组 NGX 导出
（`NVSDK_NGX_D3D12_Init / CreateFeature / EvaluateFeature / ReleaseFeature /
GetCapabilityParameters / GetFeatureRequirements / GetScratchBufferSize` 等），
内部把输入交给 `MochizukiNrRuntime.dll`，输出回 D3D12。这样 NR 就在链内、FG 之前，
`×N` 从根上消失，Magpie 的多通道与抗闪烁界面还能复用。

投入前先做**探针**：一个只记录、不干活的同名桩 DLL，打印每次调用的函数名、feature id
和参数字典键名。跑一次带 `DLSSNR` 效果的链即可确认调用序列与参数表，把工作量变成
确定值；若 Magpie 校验签名或版本，也能当场否掉这条路。

参考材料：归档 `sources\re9-presr-source.tar.gz` 里的 `OptiScaler-DLSSNR-PreSR-Multipass-main/`
已实现过 DLSSNR 的 NGX 调用序列，参数键名可直接对照。

### 6.4 已知风险

1. **停止效果组再启用会让 NR 停机**（2026-11-01 复测修正归因）：在游戏窗口点
   叉号关闭效果组后重新启用，ReShade enable 按钮旁出现红字报错、NR 失效；必须
   完全退出 Magpie 进程再启动才恢复。根因是效果组停止时 D3D12 设备未干净自毁：
   ReShade 报 `Reference count for ID3D12Device2 ... is inconsistent (35)`（同会话
   还泄漏 ID3D11Device5 ×6、ID3D12CommandQueue ×6），OpenNR 见设备销毁后置
   `off: the game destroyed its D3D12 device` 且不自愈。**此前把该红字归因为 3x
   补帧是错误的**——x2 下用同样的"关闭效果组再启用"即可复现，与倍率无关。
   3x 的真实代价是每内容帧评估三次（桥接在飞预算、光流成本 ×3），属另一件事。
2. **`History=0` 的闪烁会随补帧放大**：输出帧率越高，逐帧跳变越明显。
   开 FG 后应优先考虑把 History 开回来。
3. **光流成本回到预算里**：挂在 FG 上是必需的（1.4 ms），不能再按“白跑”处理。
4. **降分辨率不算优化**：为保持与对照运行时的可比性，`Scale` 与游戏渲染比例锁定，
   任何“提升”都必须来自真实开销下降。

## 9. 补充对账：lmxxf 82 fps 与 mochizuki 84 fps

同环境（4K 输出、NR 1080 档、`XeSS_SR` 上的 AMDOF 关、FG 关）实测：

| 运行时 | 后端 | 平衡点 | NR 总成本 |
|---|---|---|---|
| lmxxf | HIP | **82 fps** | ≈ 5.60 ms |
| mochizuki | ACO / Vulkan | **84 fps** | ≈ 5.30 ms |

两者只差 **0.30 ms**，而网络本身的差距是 **1.8–1.9 ms**（lmxxf 5.2–5.3 ms vs
mochizuki 3.4 ms）。也就是说网络的优势几乎全部被别的东西吃掉了。

把两边都拆成「网络 + 桥接」：

```
lmxxf      : 5.2–5.3 (网络) + ≈0.3–0.4 (进程内互操作) = 5.6 -> 12.2 ms -> 82 fps
mochizuki  : 3.4     (网络) + ≈1.9     (D3D11→D3D12→Vulkan 桥接) = 5.3 -> 11.9 ms -> 84 fps
```

**净差 +0.30 ms，恰好等于观测到的 +2 fps。** 这笔账到这里闭合。

### 为什么 mochizuki 的桥接要 1.9 ms

`amd-nr.log` 里写明了资源怎么跨：

```
bridge colour-in ready: 3840x2160 fmt 28, shared D3D11 <-> D3D12
bridge result-out ready: 3840x2160 fmt 28, shared D3D11 <-> D3D12
bridge: private staging 3840x2160 fmt 28, so the back buffer never meets a shared resource.
```

也就是**两次跨 API 跳**：Magpie 的后缓冲是 D3D11 → 共享到 D3D12 → 再私有一层 4K staging
→ Vulkan 网络 → 原路返回。RGBA8 4K 一次的带宽只有约 0.07 ms，所以 1.9 ms 里绝大部分
不是拷贝带宽，而是两次跨 API 的信号量/围栏等待，以及那条“后缓冲不接触共享资源”的
额外 staging 往返。

lmxxf 走 HIP，直接在 D3D12 上互操作，只有一跳，所以它的 5.2 ms 里几乎不含额外开销。

### 由此修正一条旧结论

之前写“网络我们比对方快 2.22 ms”是**只比网络**的口径，容易被误读成实机能领先 2 ms。
端到端实际只领先 **0.3 ms**。真正拉开差距的是两件事：

1. 把无人消费的光流挪出关键路径（AMDOF 1.4 ms + NR 内部 FFX 光流 2.3 ms）；
2. **桥接那 1.9 ms** ——这是目前唯一还没动过的大块。

### 桥接是下一个目标

- `NoBackBuffer` / `NoBridge` 都是**初始化期决定、且属于诊断用途**的开关
  （二进制说明：`Restart-only: Stage=%d Events=%d NoBridge=%d NoBackBuffer=%d`，
  以及 `NoBridge=1 is not read on this route`），不能当作性能选项随手开。
- 真正能减跳的方向是让 NR 跑在 Magpie 的 D3D12 设备上，而不是从 D3D11 后缓冲跨过去。
  这与第 6.3 节的 `DLSSNR` 链内槽位是同一件事：替身若在链内用 D3D12 直接取输入，
  既去掉 `×N`，也顺带消掉一次跨 API 跳。
- 若短期不动代码，可先量化桥接：用 `nrbench.exe` 在 1080 与 4K 两种光栅下对比
  “网络 + 自有拷贝”的差值，把 1.9 ms 里属于 `staging` 的部分单独摘出来。

### 口径提醒

两边的“网络时间”来自不同仪表（mochizuki 是 ReShade 自测，lmxxf 是其自有统计/离线基准），
所以拆分值有 ±0.3 ms 的不确定度。但**两个平衡点都来自 Magpie 同一套统计**，总成本
（5.6 / 5.3）是硬数，结论不受影响。

## 10. 里程碑：ACO/mochizuki 107-108 fps vs HIP/lmxxf 78-80 fps

双 addon 共存方案落地后的同场景实测（WoW 正式服、4K 输出、NR 1080 档、FG 测试链）：

| 效果组 | 钩子 | 运行时/后端 | 平衡点 |
|---|---|---|---|
| NR-mochizuki | AMDNR-ACO（纯 HLSL） | mochizuki / ACO | **107-108 fps** |
| NR-lmxxf | FSR4_SR（原生桩） | lmxxf / HIP | 78-80 fps |

**差距 27-30 fps（约 3.4-3.7 ms/帧）**，这是本轮调优最大的一次领先。此前同条件是
82 vs 84（只差 2 帧），把 mochizuki 组的钩子从 `XeSS_SR` 换成纯 HLSL 的 `AMDNR-ACO` 之后
差距彻底拉开——见 [hook-requirements.md](hook-requirements.md)。

### 10.1 88 → 105-110 的提升来源（XeSS 疑问的裁决）

用户质疑"XeSS_SR 需要 Intel ARC，9070XT 跑不了"。查证结果分两层：

**目录原文**：XeSS_SR 条目写"需要受支持的渲染 GPU 与配套 XeSS 运行库"；
"非 Intel 显卡的 3×／4× 使用本项目实验兼容路径"那句是 **XeSSFG（补帧）** 条目的。

**日志实证**（`logs/magpie.1.log:578`，两次）：

```
XeSS experimental D3D11/D3D12 backend initialized
(quality 106, Zero-MV, BGRA conversion=true, color=LDR UNORM):
3840x2054 -> 3840x2054
```

1. "跑不了"不成立：Magpie 的 **experimental D3D11/D3D12 兼容后端**在 9070XT 上确实初始化
   成功。88→105-110 的来源因此定案：去掉了一次真实 XeSS 推理（1:1、Zero-MV、带 BGRA 转换），
   约 1.6-1.8 ms/帧。
2. **"XeSS 是否真正有效"保留为疑问**（按用户要求）：日志证明它跑了，不证明它有用。
   `3840x2054 -> 3840x2054` 是 1:1、Zero-MV、experimental 路径——更像时序平滑而非超分。
   这留给后续方向 3 验证。

### 10.2 钩子需求研究（结构性结论）

详见 [hook-requirements.md](hook-requirements.md)。要点：

- OpenNR（mochizuki）挂 present 层 → 纯 HLSL 钩子正好；
- dlss5-amd（lmxxf）挂 **SR SDK 导出函数**（`ffxDispatch` / `xessD3D12Execute`）→
  必须用带原生后端的桩（`FSR4_SR`），纯 HLSL 会让它空转；
- 五个 SR 桩（DLSS/FSR2/FSR3/FSR4/XeSS_SR）的 HLSL **逐行等价**，都是一行 LINEAR 采样，
  差异只在 Magpie 调用的厂商 SDK；
- 由此两个 addon 可同时常驻，`nr-router.cmd` 不再承担文件切换。

### 10.3 后续优化方向（按优先级）

**方向 1：lmxxf 挂到真 XeSS_SR，设计 SR-NR / NR-SR 双管线**

- 已知 `FSR4_SR` 后端没有真实权重文件；XeSS 是否真正有效存疑。
- 把 lmxxf 运行时挂载到有真实 `libxess.dll` 权重的 `XeSS_SR` 上，在一个效果器里尝试
  SR-NR、NR-SR 两种管线顺序-（人工备注：SR-NR项不成立，lmxxf锁1080p，sr到4k再50%渲染率nr，必然再SR，SR-NR-SR路径已被其它项目证明不是最优解，没有意义。）
- 降低游戏窗口分辨率到 1080-2160（变相提高 lmxxf 的 NR 渲染率），用真实的 XeSS 放大，
  看实机画面效果。

**方向 2：mochizuki 提高 NR 渲染率 vs lmxxf+XeSS_SR 放大到 4K**

- mochizuki 在 1080p NR 档的帧数已过高（107-108），后续基准将提高 NR 渲染率。
- lmxxf 的网络渲染分辨率锁死 1080p，**不再做两运行时的帧数对比**；
- 改为对比两条优化路线的帧数曲线与画质：
  - (a) mochizuki 提高 NR 渲染率；
  - (b) 1080p-1440p 窗口开 lmxxf NR + XeSS_SR 放大到 4K。
