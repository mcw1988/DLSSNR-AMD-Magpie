# 路线与现状

## 愿景（一句话）

让 **AMD RX 9000 / 7000** 系显卡在 **Magpie** 里稳定跑**带帧生成的 mochizuki-ACO 权重 NR**，
网络耗时对齐上游权重自身测得的离线单帧 ms 数，在此之上把实机帧率优化上去，并配一套有效、
好调、开箱可用的 NR 风格面板。

拆成四条可验证的目标：

| # | 目标 | 怎么算达成 | 现状（2026-11-02） |
|---|---|---|---|
| 1 | **稳定**：mochizuki-ACO 在 Magpie 里长时间不崩、不掉帧、能开补帧 | 连续 30 分钟无 TDR/黑屏；FG 2x 开启后无异常 | 1080p / 9070 XT 已能输出 110–130 fps，**但帧率尚不稳定**（高负载、分辨率变化时起伏）；FG 链路在 v0.4 之后**未实测** |
| 2 | **对齐**：网络耗时 ≈ 上游离线单帧 | `nrbench` 的网络一项与上游权重给出的 ms 差 < 0.2 ms | v0.3 实机已核到「网络耗时与上游基准一致」；v0.4 改了挂载位置，**需复测并记录**（当前实机 3.27–3.40 ms @4K/1080 档） |
| 3 | **帧率**：端到端不输 lmxxf 对照实例 | 同场景、同 NR 档、同 FG 设置下 ≥ 对照 | v0.3 4K：**84 vs 82**（反超 2 帧）；v0.4 1080p：110–130（无对照数据） |
| 4 | **面板**：有效、好调、不误操作 | 面板项改动立刻可见；不含无效项；术语自解释 | 四页签已可用（网络 / 风味 / 计时 / 调试），参数经 `reno_*` 下发；**版式与术语待打磨** |

## 当前瓶颈

> 2026-11-02 更正：旧的"桥接 ≈ 1.9 ms"是 **v0.3 present 层**的残差估算，换到 v0.4 的 FFX 钩子后
> 已不成立（v0.4 每帧 CPU 合计 0.17 ms）。三段拆开与证据见 [bridge.md](bridge.md)。

1. **宿主侧的两次 4K 拷贝 + 每帧 `Flush`（结构性，改不掉）**。v0.4 起 NR 站在 Magpie 的
   `FSR3Upscaler` 里，D3D11→D3D12 由宿主用共享纹理完成：`CopyResource(sharedInput11)` →
   `Flush` → 共享围栏 → FFX → 围栏回来 → `CopyResource(output, sharedOutput11)`
   （`FSR3Upscaler.cpp:498/506/579`）。**这与 NR 无关，lmxxf 付同样的账**，是效果组的帧率下限。
   还没量过"禁用 mochinr、只留 `FSR4_SR`"的基线，所以不知道下限在哪。
2. **D3D12 → Vulkan 的每帧一次拷贝或时间线等待**。运行时优先"原地读写调用者的纹理"，失败才拷
   （二进制字符串：`frame read and written in place` / `copying instead`）。能不能原地，取决于
   Magpie 从 D3D11 共享纹理开出来的资源能否再导出句柄 —— v0.4 的 addon 已加只读探针
   （`bridge:` / `inplace=` / `copied=` 三行日志），在 9070 XT 上一跑就知道。
3. **帧内串行**：降低网络渲染率只降 GPU 负载与功率，**帧数不升**（游戏限帧已排除）。
   2026-11-02 细化：主要串行点大概率不是 Vulkan 围栏，而是 **Magpie `FSR3Upscaler` 的单槽交接**
   ——共享输入/输出纹理整会话只建一份（`FSR3Upscaler.cpp:318-319`），第 N+1 帧的 D3D11 拷入
   必须等第 N 帧的整个 D3D12 岛（NR + 放大）读完，D3D12 岛因此成为不可跨帧重叠的串行孤岛；
   该结论对 lmxxf 同样成立。三个候选解释（D3D11 侧封顶 / 捕获节奏 / `inflight` 限流）与
   判别实验见 [bridge.md](bridge.md) §8，其中 `inflight` 一个 ini 项即可试（部署包里是 2，
   代码默认 3）。
4. **分辨率**：只测过 1080p 输入；1440p / 4K 输入的拷贝尺寸与光流成本都还没调。

## 下一步（按性价比）

1. 在 9070 XT 上读新增的 `bridge:` / `inplace=` / `copied=` / `waits=` 四个读数，把第 2、3 条从
   "嫌疑"变成"数据"（步骤见 [bridge.md](bridge.md) §6）；
2. 量"禁用 mochinr、只留 `FSR4_SR`"的基线帧率，确定第 1 条的结构性下限；
3. 复测 v0.4 的网络耗时与 `nrbench` 分解，把「对齐目标 2」变成一条可复查的数据；
4. 验证补帧：v0.4 的 NR 在放大之前，FG 是否真的不再重复跑 NR（用逐帧计数对照）；
5. RDNA3（RX 7000）路线：`shaders-rdna3` 变体 + 无 ACO 的降级路径；
6. 面板：版式重排、术语统一、无效项隐藏（mochizuki 下 Compose/Guard 一类本就不生效）。

## 已知的「不算数」的结论

写在这里防止被自己的旧文档误导，细节见 [findings.md](findings.md)：

- v0.3 的「present 阶段成本随补帧倍率翻倍」在 v0.4 不再成立（NR 已挪到放大之前），但**新数字未测**；
- 「桥接 1.9 ms」是 v0.3 present 层的残差，**不属于 v0.4**（见 [bridge.md](bridge.md) §2）；
- 「网络快 2.22 ms」不等于实机领先（端到端只差 0.3 ms）；
- v0.3 的双 addon 共存方案（OpenNR 自动让位）在 v0.4 被 `nr-router` 的文件层互斥取代。

## 2026-11-02 增补（v0.5 收敛后）

1. **单槽拆解主线（已裁决 Go）**：`FSR3Upscaler` 共享纹理 2–3 槽环形缓冲，N+1 拷入与
   N 帧岛重叠。预期帧时间收益 0.5 档 −3~4.5 ms（120→约 150）、1.0 档 −7~8 ms（47→约 70），
   上下界由 B1（150 fps）/ B2（123–125 fps）实测锚定。动手前先做 inflight 2→3/4 零成本排除，
   C 组 FG 长跑当回归。
2. **Motion 线（条件触发接近成立）**：mochinr 从未接运动矢量（`fi.motion` 恒空，TEMPORAL 未解锁）；
   AMOF 已可默认开启（Performance-50% 几乎免费）——推进 kMotion → fi.motion 的成本与画质
   研究，与 AMOF 做取舍对比，TEMPORAL 接线做 A/B 画质实验后单独裁决。
