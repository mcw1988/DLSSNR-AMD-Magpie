## 3. 「50% 渲染率」到底是什么

宿主日志：

```
DLSSNR STATUS: … sourceSize=3840x2054 inputSize=1920x1027 …
                inputResolutionScaling=true inputResolutionPercent=50 …
```

运行时日志：

```
[mochizuki] building CC_SMALL_FP8 at 1920x1027 … in the RenoDX stage at 1920x1027, 1 pass
[mochizuki] session end: network 1920x1027 3.75 ms (p95 7.20, average 3.78), 54135 frames
```

**它是宿主在送进网络之前做的一次下采样**：3840×2054 → 1920×1027，NR 在 1920×1027 上跑，
再由残差合成 + catmull-rom 上采样回 3840×2054（`useResolutionScaling` 路径）。

像素账：

| 项 | 值 |
|---|---|
| 1920×1027 | 1,971,840 px |
| 1080p（1920×1080） | 2,073,600 px |
| 比值 | **95.1%**（宽 100%，高 95.1%） |
| 相对 3840×2054 | 25.0% |

⇒ 回答"是不是 1080p 或 99% 左右"：**是 1920×1027，按像素算 95.1% 的 1080p**，比 1080p 少 5% 像素。

> ⚠️ 别把这条路当成"网络渲染率 s"。两者机制不同：
> - **宿主输入下采样 50%**：NR 在 1920×1027 上跑，**残差也在低分辨率域算完**再上采样回 4K，
>   最终画面 = 原始 4K 基底 + 上采样残差 ⇒ **基底细节不丢，丢的是残差的空间精度**；
> - **网络档 s（`reno_resolution_scale`）**：输入尺寸不变，网络按 s 降档，放大后同样只影响残差精度；
>   它的基数是**输入尺寸**，不是 4K。
>
> ⚠️ 更正（2026-11-04 21:55）：本节早期写"先丢高频、画面偏软"是**错的**。
> 源码 `CompositeResidual` 的合成输入是 `{ impl.inputSrv11, verticalResidual }`，在 `sourceWidth×sourceHeight`
> 上合成 —— 底图用的是**原始全分辨率输入**，低分辨率只承担残差。
> 今天测的是前者（因为它能在面板里点）；后者要 §7.1 的通道。

## 4. 帧时间模型复核（含对我 20:32 提醒的更正）

两档实测：

| 档 | 帧时间 T | 网络（运行时口径） | T − 网络 |
|---|---|---|---|
| 4K / 100% | 19.67 ms | 18.05 ms | 1.62 ms |
| 1920×1027 / 50% | 9.61 ms | 3.75 ms | 5.86 ms |

用里程碑模型 `T = D' + I'(s)`、`I'(s) = 13.7·s²`：

**三点实测（22:28 补了 60% 档）**

| 输入档 | 网络/残差尺寸 | 像素 | 帧时间 | fps | network | T−network | 采样 |
|---|---|---|---|---|---|---|---|
| 100% | 3840×2054 | 7.89 Mpx | 19.67 ms | 50.8 | 18.05 | 1.62 | 54.6 s |
| **60%** | 2304×1232 | 2.84 Mpx | **13.12 ms** | **76.2**（平衡点 78–79） | 5.63 | 7.49 | 51.2 s |
| 50% | 1920×1027 | 1.97 Mpx | 9.61 ms | 104.0 | 3.75 | 5.86 | 520.4 s |

- `network` 与像素基本成正比（60%⟶50% 是 1.50 vs 像素 1.44），但 4K 档比线性高 15–20% ⇒ **4K 是带宽受限**，
  所以 `T−network` 在 4K 只有 1.62 ms（噪声里），在 50/60% 档才是真实固定底 **D' ≈ 6–7.5 ms**。
- 60% 档只有 51 s 采样且含启动预热，帧率按平衡点 78–79 计更可信（≈12.7–12.8 ms）。

### 4.1 时域打开（22:37 会话）：motion 与 history 都是 `TEMPORAL` 帧标志控制的

同一设置（2304×1232、s=1.0、AMDOF/Performance），唯一差别是 `MochiShimTemporal.txt=1`：

| 读数 | 22:28（无 TEMPORAL） | 22:37（有 TEMPORAL） |
|---|---|---|
| 运行时 `frame … motion` | `0x0 DXGI 0` | **`2304x1232 DXGI 34`** |
| `info: history=` | **0%** | **100%** |
| `motion_refused_dxgi` | 0 | 0 |
| 帧数 / 时长 / fps | 3904 / 51.2 s / 76.2 | 17546 / 235.4 s / **74.5** |
| network ms | 5.63 | 6.57（p95 9.53） |

**结论**：`caps.history=1`、`chained_history=1`、光流格式正确，都不足以让运行时收运动矢量；
**只有 `MOCHI_NR_FRAME_FLAG_TEMPORAL` 打开时它才取 motion 并跑历史**。
⇒ **22:37 之前的所有会话都是"逐帧独立推断"**（history 恒 0%），这就是极端旋钮值闪烁的最强解释（H1 成立）。

代价：**−1.7 fps / +0.3 ms**（network +0.94 ms），换来的闪烁抑制是肉眼可辨的。

画面侧同时出现三件事（用户实测）：

1. 「亮部」「低频时域」等参数对闪烁有明显抑制；
2. **风格 2（电影）时物体边缘闪烁加重** —— 待单独复测（怀疑与 style 的 highlight guard + 历史收敛有关）；
3. 参数偏移较大时出现明显**拖影/鬼影** —— 时域的固有问题，且 AMOF 用的是 Performance 档（矢量噪声大）。

⇒ 下一步优先验"提高光流质量能不能压住鬼影"，它直接决定时域能用多狠。

### 4.2 深度进不去；两层 + 时域 = 全屏闪烁（22:52 / 22:55）

**深度（判死）**

```
我们传： depth=0x78CE1E90 (2304x1232 DXGI 41 = R32_FLOAT)   ← 格式在头文件允许列表内
运行时： frame … motion 2304x1232 DXGI 34, depth DXGI 0      ← 仍然不收
```

`motion`（位于 `MochiNrFrameInfo` 中部）能进、`depth`（位于**结构尾部**）进不去
⇒ **这个 DLL 的 `MochiNrFrameInfo` 在 depth 之前就结束了**，尾部字段被截断。
头文件注释本身也写了"只认 struct_size 覆盖到的字段"。**这一层无解**，鬼影只能靠参数/档位规避。

**两层 + TEMPORAL（结构性冲突）**

| 读数 | 值 |
|---|---|
| 内容帧率 | 1183 帧 / 24.5 s = **48.3 fps**（2366 jobs ÷ 2 pass） |
| network | 6.26 ms（p95 10.54） |
| `panelCalls` | 2456 ≈ **每个 job 一次** SetControls（两个 pass 的控制值在交替） |
| `nrFails` | 90 ≈ 3.8% 的 job 回落直通 |

现象：**全画面、频繁跳变**（不是局部鬼影）。

主因判断：**运行时的历史是 per-session，不是 per-pass**。我们只建一个 session，
两个 pass 交替把各自的中间结果写进同一份历史 ⇒ 互相污染 ⇒ 全屏振荡。
次因（已修）：旧 shim 的 `prevJob` 只记一个 job，两层时每帧漏 `Retire` 一个（已改为 8 槽环，全量 Poll+Retire）。

**规避**：`TEMPORAL=1` 时 `Multi Pass` 必须保持 **1**。
**根治**：shim 改成"每个 feature handle 一个 runtime session"（各自历史与 job 队列），约 1 小时工作量，需实测。

**追加验证（23:03，Temporal=0 + Multi Pass=2）：仍然全画面闪烁 ⇒ 历史共享不是主因。**

| 读数 | 值 | 说明 |
|---|---|---|
| `history=` | 0% | Temporal=0 生效 |
| jobs / 失败 | 12134 / 82（**0.68%**） | job 环修复有效（此前 3.8%） |
| `job ring full` | 0 次 | 环够用 |
| `replacing the network` | 会话内 0 次 | 不是控制项抖动导致的 |
| 内容帧率 | 59.7 fps（16.7 ms） | ≈ 2×网络(5.55) + 固定底(6) |

**真正的机制（跨队列时序）**：

```
我们的 producer：跑在自己的 g_mochi.queue 上，EvaluateFeature 里**立即 Execute**
上一趟的 consumer：记在宿主的命令表（queue12）里，**帧末才 ExecuteCommandLists**
```

于是 pass2 的 `RecordInputs` 去拷 pass1 的 Output 时，pass1 的写回**还没执行** ⇒ 读到上一帧的中间结果
⇒ 输出来回跳变 ⇒ 全画面闪烁。这与实测完全吻合（不论时域开关）。

**结论**：**宿主** `Multi Pass > 1` 在本架构下不可用。v0.6 定为**面板 `Multi Pass` 恒为 1**。

### 4.3 叠层改走运行时内部 ⇒ 成立（23:19 实测，今晚最大的一条）

读旧 ReShade 路线（`mochinr.cpp:719 fi.passes`、`:619 c.reno_passes`）与上游 OpenNR
（`core/addon/mochizuki.inc:357/237`）发现：**叠层历来是"运行时在一个 job 内串行跑 N 趟"，
每趟吃上一趟的输出，从不依赖宿主多 pass。** 头文件语义一致：`passes` = "network runs per frame,
each on the previous output"。

shim 据此新增 `MochiShimPasses.txt`（1/2/3，**热生效**）：下发 `fi.passes = N` + `reno_passes = N`
+ `reno_unlock_passes = N>1`。面板 `Multi Pass` 保持 1。

**实测（23:15–23:21，同一次会话内热切，2304×1232，`Temporal=1`）**：

| 阶段 | 帧 | 时长 | fps | 帧时间 |
|---|---|---|---|---|
| 1 层 | 16825 | 215 s | 78.3 | 12.78 ms |
| **2 层（内部叠层）** | 7588 | 134 s | 56.6 | 17.66 ms |

- 叠层净成本 **ΔT ≈ 4.0–4.9 ms** ≈ 一个网络时间（用户平衡点读数 59–60 fps，走 16.7–16.9 ms）
- 运行时日志：`2 passes (was 1): history reset`、`RenoDX stage: 2 model passes a frame`、
  `network ready at 2304x1232 (model 2304x1232, up to 2 passes) in 0.5 s；the frames ran on the old one meanwhile`
- **宿主 `chain: passes=1` 全程不变**（建链次数 3，无新增）⇒ 确实没走 laterPasses
- `history=100%` 保持、`nrFails=32/24413 = 0.13%`、`job ring full` 0 次
- **画面：全屏跳变消失**，与正常两层效果类似

**残留问题（2 层特有）**：边缘拖影 + 物体几何轻微变形。两个候选：
1. **深度进不去**（§4.2 已判死）⇒ 历史重投影在轮廓处拿不到深度；
2. **没接 `MOCHI_NR_FRAME_FLAG_ANTI_HALO`**：旧 ReShade 路线在 ≥2 层时是开着的
   （`mochinr.cpp:712`），配合 `anti_halo_margin`（0..0.5，默认 0.05）限制"第二趟把像素推出第一趟局部范围"的幅度。
   我们当前 `flags=0x1`（仅 TEMPORAL），**没有这个位** ⇒ 层数上去后边缘没有约束。

下一步：接 ANTI_HALO（每帧 flag，热生效，无需重启）+ 让 `reno_look_stabilize` / `reno_detail_stability`
在面板上配合调。


| 方案 | 做法 | 代价 |
|---|---|---|
| A 一帧延迟的 fence | consumer 在宿主表上 `Signal`，下一 producer 在自己队列 `Wait` | 正确，但 pass2 要等宿主帧末提交 ⇒ 多等近一帧，帧时间大幅变差 |
| B producer 改走宿主表（**推荐**） | 多层时把 `RecordInputs` 记到宿主命令表上，与 consumer 同队列 | 需确认 `EnqueueHip` 对"列表由宿主提交"的语义；1-pass 路径保持不变以免性能回退 |

| 判据 | 模型 | 实测 | 差 |
|---|---|---|---|
| `ΔT`（两档差） | `13.7 − 13.7×0.5² = 10.28 ms` | **10.06 ms** | 0.22 ms |
| `D'`（4K 档） | — | `19.67 − 13.70 = 5.97 ms` | — |
| `D'`（0.5 档） | — | `9.61 − 3.43 = 6.18 ms` | — |

三条结论：

1. **`s²` 律成立**（ΔT 差 0.2 ms，在测量噪声内）⇒ 里程碑的 `I'(1.0)=13.7` 得到第二个点的**独立支持**，
   不再是"残差反推"。
2. `D' ≈ 6.0–6.2 ms`，比里程碑的 5.7 高 0.3–0.5 ms。方向不变（仍是"6 毫秒级的固定底"）。
3. **运行时日志的 "network ms" 不能当 `I'` 用**：它 4K 18.05 / 2K 3.75，比值 4.8（若纯按面积应为 4.0），
   说明它把 RenoDX stage 的**全分辨率编解码**也算进去了。我之前（20:32）用它推出"GPU 忙 0.92、
   应关闭线 1"，那是把两个不同口径的量混在一起 —— **撤回**。

**对线 1 的含义**（两个口径分开写，别混）：

| 口径 | 4K 忙占比 | 输出 < 160 Hz 上限 | 单槽拆解的空间 |
|---|---|---|---|
| 岛口径（运行时 network / T） | 0.92 | 55 fps | 几乎没有 |
| 纯网络口径（`I'(1.0)=13.7` / T） | 0.70 | 73 fps | 仍存在（§5.3 的 M1/M4 才能钉死） |

⇒ 先跑 **M4**（`EnableNativeBackendTiming`）把"这个 network ms 到底含不含 stage"钉死，再决定线 1 的判决。
在那之前不要在两种口径之间来回换。

## 5. 闪烁归因与抗闪烁五档实测（已定性，2026-11-05 00:45–00:52）

### 5.1 归因：H1 成立，其余降级

| # | 假设 | 判决 |
|---|---|---|
| H1 | 无运动矢量下的时域不稳定 | **成立**。`TEMPORAL` 帧标志未开时运行时 `history=0%`（22:28 会话 3904 帧全 0）⇒ 每帧从零推一遍，逐帧误差没有历史压住 |
| H2 | 极端强度进非线性区 | 次要。仍存在，但在无时域时它只是"放大逐帧差异"，不是根因 |
| H3 | 自动遮罩边界抖动 | 次要，未单独定量 |
| H4 | 半分辨率档上采样抖动 | **不成立**（100% 与 60% 档都出现） |

关键事实：`caps.history=1`、`chained_history=1`、MVec 格式正确（DXGI 34）——**全齐了运行时也不收**，只有 `MOCHI_NR_FRAME_FLAG_TEMPORAL` 打开才跑历史（详见 §4.1）。

### 5.2 抗闪烁五档实测（`Temporal=0`、`history=0%`，归因干净）

| 档 | 面板 | 实测结论 |
|---|---|---|
| 0 | None | **最终选用** |
| 1 | 静态累积 | 闪烁改善，但**拖影严重**；响应时间越高拖影越重；运动场景边缘明显模糊 |
| 2 | 光流累积 | 转视角出现"吃毒蘑菇"式扭曲（大视角变化下重投影失真） |
| 3 | 光流累积+ | 与 2 类似，稍好 |
| 4 | 低频时域重建 | 五档里效果最好，但采用与否取决于是否要时域 |

### 5.3 v0.6 最终决策：不用抗闪烁、不用时域

三条理由，都有实测支撑：

1. **所有抗闪烁档位本质都是时域**。而**深度传不进运行时**（`depth DXGI 0`，§4.2 已判死），遮挡/轮廓边缘的重投影必然拖影 —— 档位 1 的"拖影严重"与档位 2 的"毒蘑菇"同源。
2. **逐帧独立推断虽会闪，但没有拖影、没有鬼影、没有额外延迟**。用"收敛参数范围"换掉闪烁：代价是调参空间变窄，收益是画面干净。
3. **FG 插帧不依赖 NR 时域**：XeSS FG 用 Magpie 自己的光流（`motionFrames≈submissions`，§9），与运行时时域是两套独立机制，关掉后者不影响 2× 补帧。

**代价明示**：无历史 ⇒ 噪声抑制上限低于带时域方案；极端参数仍会闪，必须给参数划安全区间（见 README §3.1）。

### 7.2 去掉 ReShade（已确认可做）

**事实**：
```
dumpbin /imports Magpie.exe → … dxgi.dll …
D:\Magpie-NR-046beta\dxgi.dll = 5,592,064 字节（ReShade 6.8.0.2155）
```
Magpie 静态导入 `dxgi.dll`，而 DLL 搜索顺序把**应用目录**排在系统目录前面 ⇒ 每次启动都加载 ReShade，
present 被 hook，Home 能开面板。这就是 v0.3–v0.5 的注入入口。

**现在不需要它了**：`amdgx_dlssnr.dll` 是 Magpie 在 `DLSSNRFilter::InitializeSignedSnippetSession`
里自己 `LoadLibrary` 的（`DLSSNRFilter.cpp:1470`，日志 `Loaded DLSSNR: …\amdgx_dlssnr.dll`），
与 ReShade 无关；`mochinr.addon64` / `overlay-input.addon64` 都是 ReShade 插件，本路线已不用。

**做法**（可逆，`_test-kit\08-清理与热启\toggle-reshade.ps1`）：
把 `dxgi.dll` → `dxgi.dll.reshade-off`，`*.addon64` → 归档，`ReShade.ini` 留着无害。
系统 `dxgi.dll` 接管，Magpie 只用它的工厂/交换链创建，不需要 ReShade 的任何扩展。

**验证**：重启 Magpie 后 ①`ReShade.log` 不再更新 ②Home 不再弹面板 ③缩放与降噪照常 ④
`Loaded DLSSNR: …amdgx_dlssnr.dll` 仍出现。**回退**：文件名改回来即可。
